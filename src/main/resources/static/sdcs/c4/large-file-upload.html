Large File Upload

C4 Level 2: Container diagram. Classic example: Dropbox / Google Drive file upload.

Containers

The highlighted arrow is the point of the design: file bytes go straight from the client to object storage. No arrow carries file bytes through the Upload API.

Upload flow

  1. The user selects a file in the client app.
  2. The client asks the Upload API to start an upload (name, size).
  3. The API creates a multipart upload in object storage and saves the upload as PENDING.
  4. The API returns presigned URLs, one per part.
  5. The client PUTs each part directly to object storage.
  6. The client tells the API the upload is complete (part ETags).
  7. The API completes the multipart upload, sets the status to UPLOADED and publishes an upload-completed event.
  8. The queue delivers the event to the processing workers.
  9. The workers read the file, scan it, extract text and generate previews.
  10. The workers mark the file READY.

Assumptions

Not in the catalog entry, added to complete the diagram:

  • The user and the client app.
  • The Upload API publishes the completion event after the client calls "complete". S3 event notifications sent straight to the queue would be equally valid.
  • The protocols on the arrows (HTTPS/JSON, S3 API, JDBC).
  • The multipart steps (create, upload parts, complete with ETags), from how S3 multipart upload works.
